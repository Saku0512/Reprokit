# File Browser 認証フック教材の進行ガイド

> 対象 Lesson：`command-injection/filebrowser-auth-hook@1.0.0`。
> 状態：教材草稿。
> #9、#10、#11、#32 の接続と安全性レビューが完了するまで公開しない。

## 研修の到達点

この教材は、File Browser 2.63.5 の Hook Authentication における認証前のコマンドインジェクションを扱う。
受講者は、ログイン入力が認証フックへ届く経路、脆弱版と修正版の観察結果、修正の設計上の理由を説明する。
CVE ID は出典情報として示し、画面の主題は「ログイン入力がコマンドとして解釈される」に置く。

対象者は Web アプリケーションを開発または運用するエンジニアで、HTTP のログイン処理と環境変数の基礎を前提とする。
所要時間は 60 分を想定する。

| 時間 | 進行 | 確認すること |
| --- | --- | --- |
| 0～10分 | 背景と検証範囲 | Hook Authentication が有効な構成に限ること、ローカルLabだけを使うこと |
| 10～20分 | 入力経路の予想 | 認証前の `username` が `HookAuth.RunCommand` へ届くこと |
| 20～35分 | 脆弱版で固定マーカーを観察 | ログイン拒否と `/tmp/success` の作成を別々に確認すること |
| 35～40分 | 自分でコードを修正 | 原因箇所を探し、資格情報の受け渡しを保ったまま引数への展開を削除すること |
| 40～45分 | 修正版と差分を比較 | 同じ入力でマーカーがなく、資格情報のコマンド文字列への展開が削除されたこと |
| 45～55分 | 確認課題 | 原因、影響、修正、再発防止を本人の言葉で説明すること |
| 55～60分 | 保存と片付け | 回答保存、両Lab Sessionの停止と削除、残存確認 |

## 事前準備と実行条件

研修担当者は Lesson Version と Registry が承認した Lab ID の一致を確認する。
Lesson の `vulnerable` と `fixed` はともに `vulhub/filebrowser-cve-2026-54088` を参照し、役割を `purpose` で区別する。
同じ Lab ID の中で脆弱版と修正版を選ぶ方法は Runner 側の契約として確定する必要がある。

Lab の取得元 README には、脆弱版の認証フックを `sh -c $USERNAME` とし、ログイン入力からコンテナ内の `/tmp/success` を作る固定例がある。
この教材はその例をローカルの承認済みLabに限定する。
学習者へ任意の送信先、シェルコマンド、Compose 設定を入力させない。

**公開前の未解決点**：現行の #9 Runner API 完了条件には、コンテナ内の `/tmp/success` を学習画面へ安全に返す観察操作が明記されていない。
#9、#11、#32 の担当者と、固定マーカーの有無と必要最小限の内容だけを返す方法を合意する。
観察導線ができるまでは、Lesson の「観察結果を確かめる」を完了可能な画面として公開しない。

## 課題の採点目安

### コード修正の演習（Issue #56）

受講者画面（`/`）の「処理を見直す」の後に「自分でコードを修正する」を配置する。
公式差分を見る前に、受講者が `auth/hook.go` の `RunCommand` の学習用抜粋を編集する。
まず未修正のコードをチェックし、`cmd.Env` があっても `os.Expand` による引数への展開が残ると指摘されることを確認する。
続いて展開ループと不要になった `envMapping` の定義を削除し、`USERNAME` と `PASSWORD` を環境変数へ渡す2行を残す。
環境変数の設定は脆弱版にもあり、公式修正はこれらの行の追加ではない。
演習の元コードと次章の差分は同じ抜粋から生成し、削除した16行と変更のない4行を区別する。
ヒントは入力経路、`os.Expand` の役割、削除する処理の順に開示する。

このチェックは、教材で定義した抜粋の構造を確認する。
空白とコメントを除いた字句を既知の処理と照合し、未知の変更や構文は判定対象外として返す。
Goのビルド、受講者コードの実行、Labへの反映は行わないため、チェック成功を実環境での動作確認として採点しない。
実際の挙動は、後続の章で公式の修正版Labを用いて比較する。
実ソースの編集とビルドをRunnerへ接続する機能は、実行契約と隔離方法を決める後続作業とする。

「修正した理由」には、引数への展開を削除した理由と環境変数の受け渡しを残した理由を書いてもらう。
この欄は提出APIへ送信されず、教材一覧への移動または再読み込みで初期化されるため、採点に使う場合は既存の確認課題へ内容を転記する。

### 確認課題

`trace-boundary` では、ログインリクエストから `HookAuth.RunCommand`、`os.Expand`、管理者設定のシェルへ至る順序を確認する。
単に「入力検証が不足した」だけの回答は、信頼境界と実行経路が説明されていないため再確認を求める。

`compare-behavior` では、両版でログインが拒否されても脆弱版だけにマーカーが残る点を確認する。
HTTP の認証結果と、認証前に内部で実行された処理を分けて説明できればよい。

`propose-prevention` では、修正と再発防止を分けて評価する。
修正は資格情報のコマンド文字列への展開をなくし、環境変数として渡すことを含む。
再発防止は認証前の外部プロセス呼び出しの点検と回帰テストを含む。
回答例の全文は Lesson の `assessment[].answerExample` にあり、受講者向けの詳細 API では配信しない。

## つまずきへの対応

| 状況 | 担当者の確認と案内 |
| --- | --- |
| Lab が準備できない | Runner の取得・Lockfile・安全性検査の失敗理由を確認する。検査を迂回して元 Compose を起動しない。 |
| 接続先を取り違える | Runner が返した脆弱版または修正版の `127.0.0.1` 接続先を画面で再確認する。固定ポートを推測しない。 |
| ログイン失敗を「攻撃失敗」と解釈する | 認証結果とマーカーの観察を別の欄に書き出す。脆弱版では認証失敗前に処理が走る。 |
| 修正版でもマーカーがある | 比較前の Lab Session とコンテナの状態を確認し、別の実行から残ったファイルを混同しない。新しい修正版 Session で比較する。 |
| `os.Expand` の役割が不明 | `predict-flow` のヒントを一段ずつ開示し、文字列置換とシェルによる解釈を分けて説明する。 |
| 削除後に残存がある | Runner の残存報告に従い対象 Session のみ再確認する。手動の任意 Docker 操作を受講者へ案内しない。 |

## セキュリティレビューと公開判定

- [ ] 公式アドバイザリと修正差分が、対象版、原因、影響、対策の各記述を支える。
- [ ] 固定リクエストは承認済みのローカルLab内で `/tmp/success` だけを作り、外部通信や破壊的処理をしない。
- [ ] 脆弱版と修正版のイメージは固定 digest に解決され、Manifest、Lockfile、Compose、安全性検査を通る。
- [ ] 画面は Runner が返した loopback 接続先だけを使い、任意の対象や実行設定を受け取らない。
- [ ] `/tmp/success` の観察導線が、任意ファイル読み取りを許さない固定操作としてレビューされている。
- [ ] 回答例と評価基準は研修担当者向けで、受講者 API へ一括配信しない。
- [ ] 停止、削除、残存確認を実機の安全な fixture で検証している。
