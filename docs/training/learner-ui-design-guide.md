# 受講画面の UI デザインガイド

> 初期対象：File Browser の認証フック教材。
> このガイドは教材の見せ方と操作状態を定める。
> HTTP パス、Runner の実行方式、認証方式は #32、#9、#10 の契約に従う。

## 画面で支える学習の流れ

受講者は「背景を読む → 結果を予想する → ローカルLabで手動確認する → 観察を書く → 原因と修正を比較する → 回答する → 片付ける」の順に進む。
各画面は一つの判断または操作に集中させる。
CVE ID は出典欄に置き、画面の見出しには現象を表す Lesson の題名を使う。

デスクトップでは学習内容と Lab 状態を並べる。
狭い画面では Lab 状態を学習カードの前に置き、横スクロールを必要としない。

```text
┌──────────────────────────────────────────────────────────┐
│ Reprokit  教材名                              進捗 3 / 8 │
├───────────────────────────────────┬──────────────────────┤
│ 現在のステップ                    │ Lab 状態             │
│ 目的 → 予想 → 手順 → 観察         │ 脆弱版 / 修正版      │
│                                   │ 検査・接続先・失敗   │
│ ヒントを一つ開く                  │ 準備 / 起動 / 停止   │
│ 観察メモ                          │                      │
│ 戻る                         次へ │                      │
└───────────────────────────────────┴──────────────────────┘
```

## 情報の優先順位

教材詳細では、題名、学習目標、対象者、前提知識、所要時間、ローカルLab限定の注意を先に示す。
製品名、対象版、CVE、公式出典、ライセンスは同じ画面の根拠欄に置く。
Lab が未準備でも背景と学習目標を読めるようにする。

各ステップのカードは次の順序にする。

1. **目的**：この段階で説明または確認すること。
2. **予想**：受講者が先に考える問い。回答はローカルに保存する。
3. **手順**：対象 Lab、Runner が返した接続先、固定の操作例。
4. **観察**：受講者が確認した結果と Lesson の期待結果。
5. **ヒント**：要求された分だけ一つずつ開く。
6. **次へ**：観察を記録してから進める。戻っても回答と開示済みヒントを保持する。

期待結果は予想を記録する前に強調表示しない。
回答例と評価基準は研修担当者向けに保ち、受講者向けの教材詳細や画面データに含めない。

## Lab 操作と失敗時の表示

Lab の状態は `absent`、`preparing`、`prepared`、`starting`、`running`、`stopping`、`stopped`、`deleting`、`deleted`、`error` を文字でも表示する。
色だけで状態を伝えず、状態名と次にできる操作を併記する。
脆弱版と修正版の状態、接続先、Session ID は混同しないよう別のカードに置く。

`Prepare` は取得と検査までの操作として表示し、起動ボタンを同時に実行しない。
`Start` は安全性結果を見せた後に明示確認を求める。
`Stop` と `Delete` は別のボタンにし、削除時だけ定義済みの Volume 方針を選ばせる。
失敗時には Runner が返した失敗理由、再試行の可否、安全な次の操作を示す。
学習進捗と Lab 状態は独立して表示し、Lab の起動成功を教材修了と扱わない。

初期教材の固定リクエストはテキストとして表示し、受講者が Runner の loopback 接続先を確認して手動で送る。
画面は任意の対象 URL、Compose、Docker 引数、イメージ、ホストパス、シェルコマンドを入力させない。
固定例のコピー操作を設ける場合も、コピー内容と送信先の注意を同じ場所に表示する。

`/tmp/success` の観察には、任意ファイルを指定できない専用の固定操作が必要である。
現行の #9 完了条件にその操作は明記されていないため、Runner 契約と安全性レビューが終わるまで観察ボタンを有効にしない。

## 視覚ルール

画面の背景は `#F8FAFC`、本文は `#0F172A`、補足文は `#475569`、操作の主色は `#1D4ED8` を基準とする。
カードは白背景と細い境界線で分け、警告は色に加えて見出しと説明文で伝える。
本文は 16 px 相当以上、行間は 1.5 前後を基準とし、日本語の長文は一行が長くなり過ぎない幅に収める。
余白は 4、8、12、16、24、32 px の段階を使い、操作群と説明文のまとまりを揃える。

ボタンには常に動詞を含める（例：「Lab を準備する」「安全性を確認して起動する」「次のヒントを開く」）。
危険度の高い削除操作は主操作から離して配置し、対象 Session と Volume 方針を確認画面に再表示する。
処理中はボタンの状態と進捗文を更新し、完了または失敗まで同じ操作を重複送信させない。

## キーボードと小画面

主要操作はキーボードだけで到達・実行できる順序にする。
フォーカス位置を常に視認できるようにし、ダイアログを開いた後は内部へ、閉じた後は元の操作へフォーカスを戻す。
ヒントを開いたこと、Lab 状態の変化、保存結果、失敗理由は画面読み上げでも伝える。

小画面では学習カードを一列にし、Lab 状態と接続先を現在のステップの近くに置く。
横長のコードや JSON は領域内で折り返しまたは横スクロールさせ、画面全体を横に動かさない。
固定の「次へ」ボタンを使う場合は、本文や安全性の注意を隠さない。

## #11 の画面レビュー項目

- [ ] 初学者が Lesson の目的、前提、所要時間、ローカル限定の注意を開始前に確認できる。
- [ ] 予想、手動操作、観察、原因の順序が画面上でも保たれる。
- [ ] ヒントは一段ずつ開き、回答例は受講者へ送られない。
- [ ] 脆弱版と修正版の接続先と状態を取り違えにくい。
- [ ] 準備、明示起動、停止、削除、残存確認を区別できる。
- [ ] Runner 以外へ Docker 操作を送らず、任意の実行設定を入力できない。
- [ ] キーボードだけで主要操作を完了でき、失敗理由を読み取れる。
