# Reprokit プロダクト方針 — セキュリティ教育への全面転換

> **決定：2026-10-14。** Reprokitの主目的・評価軸・開発優先順位を、脆弱性検証環境の管理から**初学者向けの体験型セキュリティ教育**へ全面的に転換する。以前の技術設計は教材の裏側で動く基盤として継承する。機能は現在開発段階で、教材やUIが実装済みという意味ではない。

## 一言で説明すると

**「実際のCVEを、自分で試して理解する。」**

Reprokitは、セキュリティを学び始めた人が、公開されたCVEの脆弱性を、管理されたローカル環境で**読んで、試し、観察し、原因と対策を理解する**ためのOSS学習ツール。

環境を取得・起動できることは製品の**目的ではなく手段**。学習者が「何が問題だったのか」「どう修正すれば防げるのか」を説明できる状態をゴールとする。

## 検証環境の採用方針（2026-10-15更新）

**MVPは[Vulhub](https://github.com/vulhub/vulhub)の既存Docker Compose検証環境を再利用する。** Reprokitは脆弱な環境そのものを大量に作るのではなく、初心者がWebで脆弱性の説明を読み、**自分でPoCを試し、結果・発生原因・修正方法まで理解する体験**に注力する。

PoCはローカルLabを対象に学習者自身が実行する。Webには手順、コピー可能な例、期待結果、ヒントを表示するが、任意のシェルやPoCを無条件に実行しない。詳細：[Vulhub連携・教育MVP](vulhub-learning-mvp.md)。

## メインターゲット

- セキュリティ分野の勉強を始めたい学生・独学者・初学者
- CVEの名前は聞いたことがあるが、実際に再現した経験がない人
- 環境構築に時間を使うより、脆弱性の仕組みを実物で確かめたい人

**前提知識を最小化する。** CVEとは何か、HTTPやコンテナとは何かなどは教材側で必要に応じて説明する。初期段階でDockerなどのローカル実行基盤が必要なことは隠さず、導入の難しさをUX改善課題として扱う。

## 提供価値と優先順位

| 優先度 | 学習者の体験 | 実装の役割 |
| --- | --- | --- |
| 最優先 | 何を学べるのか選べる | 難易度、ジャンル、前提知識、目標を提示 |
| 最優先 | なぜそのCVEが生じたか理解できる | 日本語中心の簡潔な解説と信頼できる参照元 |
| 最優先 | 自分の操作で脆弱な動作を確認できる | 段階的な演習、ヒント、観察ポイント |
| 最優先 | 防御・修正方法まで理解できる | 根本原因、対策、振り返り |
| 基盤 | 同じ実験環境を扱える | **Vulhubを主なLab提供元**とし、Registry → Manifest → Lockfile → Runtimeで参照・管理 |
| 基盤 | 安全に終了できる | 起動前警告、ローカル隔離の限界、停止・削除 |
| 後段階 | 進捗の保存・難易度別の学習経路 | 履歴、達成状況、学習パス |
| 後段階 | 大量のCVEを網羅する | 教材の質を優先し、無差別な大量収録はしない |

## 学習の基本フロー

1. **探す**：CVE IDに加えて分野（XSS、パストラバーサル等）や難易度・前提知識から教材を選ぶ。
2. **理解する**：CVE、影響範囲、脆弱性の前提、学習目標、注意点を読む。
3. **準備する**：環境の取得・固定、ポート・権限・リスクの確認。**createはコンテナを起動しない**。
4. **試す**：明示的に環境を起動し、**学習者自身が**記載された手順を安全なローカル環境で実施する。
5. **観察する**：期待される結果と自分の結果を照合し、ヒントを必要に応じて表示する。
6. **理解を深める**：原因となる挙動、修正方法、影響範囲を学び、振り返る。
7. **片付ける**：環境を停止・削除する。教材がクリーンアップの意味を説明する。

## 技術設計の再位置付け

- **Manifest（既存）**：CVEが紐付いた実験環境の取得方法を宣言。学習本文を詰め込まない。
- **Registry（既存）**：環境の所在を検索する。将来はカテゴリや教材の検索索引とも連携する。
- **Lockfile（既存）**：教材の環境条件が再取得後も追跡できるようにする。
- **Lesson（新規概念）**：学習目標・説明・難易度・前提知識・手順・ヒント・観察点・根本原因・対策・後片付けを定義する。
- **学習インターフェース（採用済み）**：初心者はローカルWeb UIで教材を学び、同じGo CoreをCLIとWebから使うハイブリッド構成。詳細は[UI設計](interface-study.md)。

**LabとLessonは分離**する。1つのLabに複数Lessonを紐付けることも、同じCVEに複数の難易度の教材を作ることも可能にする。対応Labがあるだけでは教材が完成した扱いにはしない。

## MVPの成功条件を改定

**「CVEの環境を動かす」だけではMVPの成功としない。**

- 初学者が教材を1つ選び、目標と前提を理解できる。
- 対象CVEの隔離されたローカル環境を取得・明示起動できる。
- 日本語の説明、段階的な実験手順、ヒントと観察ポイントが用意されている。
- 動作を観察し、脆弱性の原因と**防ぎ方**まで説明できる。
- 脆弱環境を停止・削除できる。危険なネットワーク公開を促さない。
- 最低1つの教材で、初心者が最後まで操作できるかを検証する（学習者テスト）。

## 何を目指さないか

- CVEを指定すると任意の対象へ自動攻撃するツール
- 実サイトへの攻撃手順を自動化する仕組み
- CVEごとの環境を網羅するだけの巨大カタログ
- セキュリティ専門家向けの検証効率だけを最重要視した製品

## 安全性と責任範囲

教材は許可されたローカル環境で実施する。脆弱なサービスは明示起動、公開ポートは原則ループバックに限定し、Dockerの完全隔離を保証しない。教材の例は無害な観察・検証を優先し、第三者システムを対象にさせない。必要に応じて隔離VMでの実施を案内する。

## MVPの優先順位（2026-10-15更新）

まず**VulhubのLabを用いた学習教材を1本、Web上で最後まで完走できる状態にする**。PoCを使った観察と原因・対策までが必須。Registryの高度化、Providerの一般化、大量のCVE登録は後回しとする。
